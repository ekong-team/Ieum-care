# 한수 담당 분석: 원본에서 우선 지원 대상과 다음 에이전트 입력까지

2026-10-20 기준. 이 문서가 현재 분석 흐름의 시작점이다. 한수 브랜치의 담당 범위는 **제공 자료 분석 → 활동 위축 1~5단계 → 원인 가설·주요 특성 → 위험 단계만으로 정한 1차 우선 검토 순위**다. 복지자원 추천 후 자원 부족을 반영하는 2차 우선순위는 포함하지 않는다.

## 1. 전체 흐름부터 보기

```text
제공 원본: 통신18개 + 카드2개
  → 원본 구조·중복·수치·지역·월 검증
  → 통신 특징 / 카드 특징
  → 월×지역×연령 합산 특징72행
  → 일평균 소비·업종 제외 민감도 / 주민인구·달력 배경
  → 원본 성별로 다시 계산: 남녀144행 + 합산72행 =216행
  → 분석 입력 검사
  → 파이썬으로 변화율·1~5단계·부분판정·보류 계산
  → 근거·가설·특성·배경 정리
  → 선택 집단만 Tavily 검색·Gemini 검토 (옵션)
  → 동일 기준월의 남녀24집단 1차 순위 / 합산12집단 별도 비교
  → JSON·대상별 프로필·한국어 설명·검증 결과 저장
  → 정욱 공통 프로필 또는 현지 기준 입력으로 전달
```

**변화율·단계·순위는 파이썬 계산이다. Gemini가 고립 위험 점수를 마음대로 정하지 않는다.** 외부 검색은 설명을 보완할 참고 후보를 찾는다. 인터넷에서 숫자를 찾았다고 자동으로 기존 데이터에 합치지 않는다.

## 2. 데이터의 실제 단위

| 구분 | 실제 의미 | 주의할 해석 |
|---|---|---|
| 통신 AGE | 소지역·좌표·월별 연령/성별 관측 유동량 | 통신요금·통화비·고유 방문자 수가 아님 |
| 통신 TIME/WKDY | 시간대·요일별 관측 활동 맥락 | 연령·성별 전용 관측이 아니므로 남녀별 독립 근거로 사용하지 않음 |
| 카드1 | 가맹점 지역·업종·연령·성별 집계 결제건수/금액 | 사람 수나 실제 대면 교류 횟수가 아님 |
| 카드2 | 거주지 구분 등이 포함된 별도 집계 | 카드1과 겹칠 수 있어 둘을 합산하지 않음 |
| 주민등록 인구 | 해당 지역에 등록된 주민의 연령·성별 인구 | 방문객이 섞인 활동량의 분모나 고립 위험 인원으로 사용하지 않음 |
| 달력 | 월 일수·주말·공휴일 | 개인별 휴무일·계절 효과의 완전한 보정이 아님 |

자료는 동일 개인으로 연결되어 있지 않다. 결과는 지역·연령·원본 성별 구분의 집단 관측이며 개인 진단·확정 지원 자격·고립 확률이 아니다.

기간은 2025년7~12월, 지역은 강남구·춘천시, 연령은10~19세/20대/30대/40대/50대/60세이상이다. 6개월×2지역×6연령=합산72개, 성별2개를 나누면144개다. 합산은 남녀와 중복되는 비교 자료이므로216개를 서로 독립인 인구집단으로 세지 않는다.

## 3. 원본 파일을 어디에 놓는가

```text
data/raw/
├─ flow_age_pop_202507.csv … 202512.csv    # 연령·성별6개
├─ flow_time_pop_202507.csv … 202512.csv   # 시간대6개
├─ flow_wkdy_pop_202507.csv … 202512.csv   # 요일6개
├─ 신한카드_빅콘테스트2026_데이터1.txt
└─ 신한카드_빅콘테스트2026_데이터2.txt
```

통신은 `|` 구분, 카드는 탭 구분·CP949 인코딩이다. 원본은 수정하지 않는다. 원본·가공 결과·키·가상환경은 Git 제외다. 팀원이 코드를 받는 것과 보유 원본/배경자료를 준비하는 것은 별도다.

## 4. 원본 검증과 통신 정제

| 파일 | 입력 → 처리 → 출력 |
|---|---|
| `scripts/data_processing/data_contract.py` | 공통 월·지역·연령·필수 열·중복 키·수치 검증 및 안전한 나눗셈. 현재 제공 기간 설정도 여기에 있음 |
| `scripts/data_processing/build_telecom_features.py` | 통신18개 → 완전 중복만 제거·월/좌표/수치 검사·AGE/TIME/WKDY 특징 → `data/processed/telecom_features.csv` |

통신의 한 행은 `STD_YM + BLOCK_CD + X_COORD + Y_COORD`이다. 같은 키에 내용이 다른 중복이 있으면 임의로 더하지 않고 중단한다. 세 자료의 관측 위치가 다를 수 있어 outer 결합으로 차이를 보존하고, 관측이 없다는 이유로0을 넣지 않는다.

합산 특징에서는 MAN+WMAN으로 연령 유동량을 만든다. 시간대는 새벽·주간·저녁 비중, 요일은 평일/주말 평균 등으로 정리한다. 이 단계의 통신 일부 `PCT` 열은 −10이 −10%이고, 최종 위험 특징의 변화율은 −0.1이 −10%다. 서로 혼동하지 않는다.

## 5. 카드 정제와 업종 분류

| 파일 | 입력 → 처리 → 출력 |
|---|---|
| `scripts/data_processing/industry_classification.py` | 원래 업종 이름 → 목적별 업종 그룹. 포괄 업종은 해석보류, 처음 본 업종은 미분류 |
| `scripts/data_processing/build_card_features.py` | 카드1·2 → 법인 표시 일치 검사·개인 기록 선택·연령 통합·지역/업종 집계 → `card_features.csv`, `industry_classification_review.csv` |

성별이 법인인데 연령은 개인처럼 기록된 경우 등은 오류로 중단한다. 60·70·80·90대는60세이상으로 통합한다. 카드1의 금액과 건수, 카드2의 금액과 건수는 각각 별도 열로 보존한다.

단계 계산의 핵심 소비 지표는 **카드1 개인 결제건수의 일평균 전월 변화율**이다. 금액은 물가·단가 차이가 섞일 수 있고, 건수도 개인 수·관계 활동 그 자체가 아니라는 한계가 있다.

## 6. 통신과 카드의 합산 특징 결합

`scripts/data_processing/build_risk_features.py`가 두 특징을 `월×지역×연령대`로 맞춰 `data/processed/risk_features.csv`를 만든다. 현재72행이다.

1. 통신 소지역코드 앞5자리로 대상 지역을 식별한다. 강남11230·춘천32010은 여기서 쓰는 통계청 코드다. 다른 체계의 지역코드와 섞지 않는다.
2. 대상 밖 지역을 강남·춘천으로 강제로 바꾸지 않는다.
3. 연령별 열을 행으로 펼친다.
4. 지역·연령별 월 자료를 카드와 결합한다.
5. 통신 전월 변화는 **두 달 모두 관측된 공통 위치**의 합계끼리 비교한다. 관측 위치가 바뀐 효과와 활동 변화가 섞이는 것을 줄이기 위해서다.

통신 변화율은 `현재 공통 위치 유동량 합계 / 전월 같은 위치 유동량 합계 − 1`이다. 관측 범위가 완전히 같아졌다거나 구성 변화가 모두 제거됐다는 뜻은 아니다.

`scripts/data_processing/analyze_features.py`는 EDA·업종 민감도·입력 후보를 정리한다. `validate_processed.py`는 특징·분석 기록 검증을, `validate_regions.py`는 지역코드·좌표·경계 검토를 맡는다. 공간 결과는 좌표 해석 조건과 예외를 함께 읽는다.

`run_preprocessing.py`는 통신정제→카드정제→특징결합→기초분석→검증을 순서대로 실행하는 진입점이다. **이 명령 하나로 최종 성별 Agent와 외부 API까지 모두 실행되는 것은 아니다.**

## 7. 일평균·업종 민감도와 배경자료 준비

### 카드 일평균과 골프·놀이동산

`scripts/data_processing/analyze_card_complete.py`가 원본 카드와 기존 특징을 읽어 일평균·업종 변화·지역 전체 변화 등을 계산한다. 성별 준비 단계가 사용하는 출력은 `data/processed/eda/card/golf_leisure_sensitivity.csv`다.

```text
하루 평균 건수 = 월 결제건수 / 그 달의 달력 일수
소비 변화율 = 현재 하루 평균 / 전월 하루 평균 − 1
```

31일과30일의 월합계를 그대로 비교하면 일수 차이가 섞이므로 일평균을 기본으로 선택했다. 개인당 소비로 바꾼 것은 아니다.

골프·종합레저타운/놀이동산을 **전체 분석에서 삭제한 것은 아니다.** 특정 업종의 계절성·지역 특성에 결과가 좌우되는지 보기 위해 제외했을 때도 감소가 유지되는지 추가 비교한다. 기본 E1은 전체 카드1 개인 건수다.

현재 실행은 이미 준비된 배경 패킷과 인구 CSV를 입력으로 사용한다. 이 배경자료는 Git에 포함하지 않는다. 새 PC에서는 함께 준비하거나 위 보조 코드와 보유 원본으로 재생성해야 한다. 과거 보고서 재생성에는 `requirements-analysis.txt`의 그래프 패키지도 필요하다.

기온·물가 조사 코드와 결과는 탐색 경위 재현용으로 보존되어 있지만 현재 단계의 가중치나 최종 배경 입력으로 채택하지 않았다. 외부 검색으로 검색됐다는 이유만으로 이를 자동 채택하지 않는다.

## 8. 성별을 나누는 핵심 파일

`scripts/data_processing/build_sex_features.py`는 이미 합산된72행을 억지로 반으로 나누지 않는다. **원본 카드1·원본 통신 AGE를 다시 읽어 남녀 각각 계산한다.**

1. 카드 `남성/여성`과 통신 `MAN/WMAN`을 `male/female`로 명시 변환한다.
2. 월×지역×연령×성별로 카드 건수·일평균·업종 제외 건수를 다시 집계한다.
3. 같은 성별·같은 연령의 인접 월 공통 통신 위치로 유동량 변화율을 계산한다.
4. 남녀 건수 합이 합산 건수와 정확히 같고, 유동량 합도 허용 수치 오차 내에서 같은지 검사한다.
5. 남녀 변화율을 단순 평균하지 않고 각각의 원래 합계·분모로 계산한다.
6. 동일 성별의 주민 인구와 지역 전체 소비 변화, 달력 배경을 연결한다.
7. 남녀144행과 합산72행을 함께 저장한다.

출력 폴더의 의미는 다음과 같다.

| 출력 | 내용 |
|---|---|
| `features.csv` | 계산에 사용할216개 월·지역·연령·성별 특징 |
| `sensitivity.csv` | 전체 카드 일평균과 골프/레저 제외 변화율 |
| `context.json` | 인구·달력·업종/지역 특성 설명용 패킷 |
| `sex_measurements.csv` | 성별 원래 집계 건수·유동량 등 확인용 |
| `sex_preprocessing_manifest.json` | 원본·기준 파일·전처리 코드·출력의 SHA-256과 남녀 합산 일치 검사 결과 |

현재 제공 기간·파일명·지역 범위는 고정되어 있다. 다른 연도 원본을 넣기만 하면 자동 전처리되는 범용 수집기는 아직 아니다. 핵심 단계 계산은 적절한 입력 형식의 다른 연도도 처리할 수 있다.

## 9. 분석 Agent의 모듈별 입력·처리·출력

| 파일 | 입력 | 하는 일 | 출력 |
|---|---|---|---|
| `inputs.py` | features/sensitivity/context·manifest | 필수 열·수치·집단 키·월·성별·출처 해시 검증 | 검증된 행 목록·배경 사전·출처 목록 |
| `policy.py` | 코드 설정 | 지역·연령·성별·3/5%·민감도 기준과 해석 한계 정의 | 여러 모듈이 공유하는 기준 |
| `assessment.py` | 검증된 행 목록 | 일평균 변화·동시 감소·지속성·상위 조건 계산 | 집단별 단계/상태/조건/수치/경고 |
| `interpretation.py` | 집단별 계산 결과 | E1~E3 근거·허용된 원인 가설·팀 프로필 생성 | profile·hypotheses·team_causes |
| `context.py` | 계산·배경·민감도 | 집단/수치 일치 확인, 인구·달력·지역/업종 특성 병기 | 상세 cohort216개 |
| `reviewer.py` | 선택 cohort | 모델 출력의 근거·가설·질문 번호를 검증 | model_review·실행 수신 기록 |
| `gemini_provider.py` | 선택 집단 요약·가설·배경 | Tavily·Gemini API, 키/호출 상한/오류 관리 | 구조화 제안·출처·호출/사용량 기록 |
| `research.py` | 프로필·검색 발췌·모델 인용 | 질문별 검색계획·목록/범위/인용 검사·한국어 설명 | 참고 후보/제외 사유·설명 보고서 |
| `priority.py` | 상세 cohort·기준월 | 완료 판정만 단계 내림차순·동률 처리 | 1차 순위와 별도 부분/보류 목록 |
| `workflow.py` | rows·contexts·manifest·기준월 | 실제 LangGraph로 전체 순서 실행 | analysis bundle 딕셔너리 |
| `handoff.py` | bundle·analysis_id | 팀 공통 프로필 또는 정욱 원인 노드 어댑터 생성 | TargetProfile·analyze_causes 함수 |
| `welfare_handoff.py` | 단일 cohort | 성별을 보존한 한수 기준 요청으로 변환 | request_v02·상세 handoff record |

`run_analysis_agent.py`가 실행 파일이고, `workflow.py`의 `run_analysis()`가 다른 코드에서 import하는 함수다. LangGraph 노드는 `calculate → describe → interpret → first_priority`다. 여러 노드가 있다고 계산 노드까지 모두 LLM Agent인 것은 아니다.

## 10. 1~5단계는 정확히 어떻게 결정하는가

기본 기준은 두 지표 각각 전월 대비3% 이상 감소다. −3%도 포함한다. 큰 감소 기준은5%다. **연구에서 검증된 진단 임계값이 아니라 프로젝트의 시범 가정**이다.

| 단계 | 판정 조건 |
|---|---|
| 1 | 카드·통신 모두3% 이상 감소 조건에 해당하지 않음. 고립 없음·안전 확정이 아님 |
| 2 | 카드·통신 중 하나만3% 이상 감소 |
| 3 | 현재 카드·통신 둘 다3% 이상 감소 |
| 4 | 현재와 직전 전월 비교에서 모두 동시 감소. 비교 두 번에는 원자료 세 달이 필요 |
| 5 | 4단계 조건 + 현재 두 지표 모두5% 이상 감소 + 골프/레저 제외 소비도 두 번 연속3% 이상 감소 |

필수 전월 비교가 없으면 `held`로 두고 단계는null이다. 일부 상위 조건만 모르고 하위 단계는 성립하면 `partial`로 보존한다. 예를 들어8월 첫 동시 감소는7월의 전월 비교가 없어 지속성을 확정하지 못할 수 있다. 모르는 값을0이나 낮은 위험으로 바꾸지 않는다.

`complete`는 **정한 규칙의 계산 조건을 판정할 수 있었다**는 뜻이다. 실제 고립이 확인됐다는 뜻이 아니다. 관측률90%·75% 경계는 진단용 경고이며 현재 단계를 강제로 낮추는 차단 조건으로 쓰지 않는다.

민감도는 월합계3%, 일평균2%, 일평균4%와 기본 일평균3%를 비교한다. 기준을 조금 바꾸면 단계가 달라지는 집단은 결과와 함께 알려주며 가장 높은 결과를 골라 사용하지 않는다.

## 11. 실제 사례로 읽기

2025년12월 춘천30대여성은 카드 일평균−6.62%, 공통 위치 유동량−4.57%, 동시 감소 비교2회로4단계다. 유동량 감소가5% 미만이므로 현재 큰 감소 조건을 충족하지 않는다.

같은 집단의 주민등록 인구는16,633→16,636명(+0.018%)이었다. 주민 인구 감소가 함께 나타난 사례는 아니지만, 활동지역 집계와 주민 인구의 대상이 다르므로 이것만으로 원인을 확정하지 않는다. 해당 월31일, 주말·공휴일 합계9일이라는 기존 달력 맥락도 병기한다.

원인 가설은 소비·유동량 동반 위축(C3), 신호 지속(C4) 등 **관측 기반 확인 후보**다. 외로움·경제 곤란·정신건강 상태·지원 필요를 실제로 확인했다고 쓰지 않는다.

## 12. Tavily·Gemini가 하는 일

기본은 외부 API를 호출하지 않는다. 명시적으로 켠 선택 집단만 검토한다.

- basic: 넓은 검색1회+Gemini1회. 첫 연결 시험용.
- focused: 인구·지역 경기·달력별 검색 각1회(최대3회)+Gemini1회.
- focused는 분석월 이후 발표된 통계도 찾는 사후 해석용이다. 과거 실시간 판단에 사용할 수 있었다고 주장하지 않는다.
- Gemini는 기존 근거·가설·질문 번호와, 적합한 외부 참고 후보가 있을 때만 실제 발췌 인용과 관련성을 제안한다.
- 프로그램은 공식 HTTPS 주소·목록 페이지 여부·지역/기준월/주제·인용 존재를 검사한다. 검색 홈페이지·게시판 목록을 수치 근거로 승격하지 않는다.
- 범위·인용 검사는 원문 통계 단위·표본·인과관계의 사실 확인을 대신하지 못한다. 관련성 해석은 별도 검증 전 모델 해석이라고 표시한다.
- 키·한도 오류가 나면 남은 검색을 중단한다. 실패 시 자동 재시도·유료 모델 전환 없이 기존 분석을 보존한다.

2026-10-20 실제 focused 시험은 검색3회·Gemini1회로 완료했다. 인구 게시판과 일반 페이지 등 발췌4개를 확보했지만 수치·원인 보완 인용은0개였다. Gemini는 없는 근거를 만들지 않았다. 경기 자료는 확보하지 못했다. 검색 성공과 분석 근거 확보를 같은 것으로 표현하지 않는다. 이후 로컬 재점검에서 게시판 목록 검사를 더 강화했으며 추가 API는 호출하지 않았다.

무료 Gemini 입력·출력은 서비스 개선에 사용될 수 있다. 계정의 무료 등급·한도는 별도로 확인한다. 키만으로 비용0원을 보장할 수 없다. 사용자 승인 범위 밖의 다른 집단·대량 호출을 자동으로 수행하지 않는다.

## 13. 우선 지원 대상 순위는 어떻게 나오는가

기준월 하나를 고른다. 기본202512다. 남녀별 자료가 있으면2지역×6연령×2성별=24집단을 대상으로 한다.

1. `complete` 집단은 단계가 높은 순서대로 정렬한다.
2. 같은 단계는 모두 공동 순위다. 예를 들어4단계가 셋이면 셋 모두1순위, 다음3단계는2순위인 밀집순위다.
3. 같은 순위 안의 analysis_id 정렬은 표시 순서일 뿐 우선성 차이가 아니다.
4. `partial`은 별도 목록에, `held`는 별도 보류 목록에 남긴다.
5. 민감도·품질 경고를 함께 전달하되 임의로 점수 가중치를 더하지 않는다.
6. 합산12집단은 별도 파일로 비교한다. 남녀와 합산을 같은 순위표에 섞지 않는다.

12월 남녀 공동1순위는 **춘천30대여성·춘천30대남성·춘천40대남성**이다. 모두4단계다. 단계3미만을 자동 탈락시키는 임의 기준은 없다. 이 결과는 활동 위축 검토의1차 목록이며 인원수·지원 자격·확정 고립 순위가 아니다.

복지자원이 부족한지를 반영하는2차 우선순위, 복지 추천, 새 프로그램 기획, 기획안 평가 점수 정렬은 이 함수의 역할이 아니다. 정욱 그래프의 기획안 priority_report와 지역·계층의1차 순위를 구분한다.

## 15. 다음 Agent에게 무엇을 보내는가

### 정욱 공통 흐름으로 연결

`ai/contracts/profile.py`의 `TargetProfile`(target-profile-0.2)이 공통 입력이다. `handoff.target_profile(bundle, analysis_id)`로 검증된 객체를 얻는다.

```python
from ai.analysis_agent.handoff import target_profile, make_cause_engine

profile = target_profile(bundle, "202512_32010_30G_female")
cause_engine = make_cause_engine(bundle)
# 정욱 Engines.analyze_causes 자리에 cause_engine을 주입하는 연결점이다.
# 이 두 함수를 불렀다는 것만으로 전체 기획·추천·평가 흐름이 자동 연결되지는 않는다.
```

프로필에는 `target(region, age_group, sex)`, `period`, `risk(level,status,model_version)`, `evidence(E1~E3)`, `signals`, `limitations`, `is_example`이 있다. 예를 들어 이 사례의 target은 춘천시/30/female, period는2025-12, risk는4/complete다.

E1은 카드 변화율, E2는 유동량 변화율, E3는 동시 감소 비교 횟수다. `make_cause_engine`은 이 프로필과 정확히 일치하는 기존 원인 가설을 반환하고, 검증된 모델 선택은 강조 순서·추가 확인 질문에만 반영한다.

### 현지 복지 추천으로 연결

`welfare_handoff.to_welfare_request(cohort)`가 **한수 기준 risk-input-0.2 계약**을 만든다.

```text
target: 지역·연령·성별·목적
risk_assessment: 분석ID·지역·연령·성별·기준월·단계·상태·신호·한계·버전
confirmed_support_needs: []  # 실제 확인 전에는 욕구를 만들어 넣지 않음
```

현재 병합한 현지의 risk-input-0.1은 성별 필드를 받지 않는다. 남녀별 자료를 그대로 보낼 수 있는 연결 완료 상태가 아니다. 사용자가 한수 출력 risk-input-0.2를 기준으로 확정했고, 현지 수신부가 이 형식에 맞춘다. 한수 쪽 계약 제공은 완료이며 수신 검증·모델 입력·응답의 적용은 현지 담당이다. 정욱의 변환 함수도 같은 계약을 보존해야 한다. 분석10대는10~19세인데 현지10구간은0~19세인 차이도 맞춰야 한다.

`to_current_aggregate_request`는 합산 자료만 기존0.1로 변환한다. male/female 입력은 성별을 버리지 않고 거부한다.

`handoff_record`는 profile·request_v02·상세 analysis_context를 나눠 보존한다. 상세 context 전체를 현재 HTTP 요청에 임의로 붙이지 않는다. 검색 결과도 새로운 E번호 숫자로 프로필에 합치지 않는다. 다음 Agent가 외부 자료를 사용할 때는 별도 참고 자료로 받아 같은 한계를 지켜야 한다.

`build_welfare_handoff_package.py`는 전달용 ZIP과 규격·예시·216개 프로필·순위·설명서를 만들고 `check_welfare_handoff.py`가 해시·규격·집단 일치를 검사한다. 자동으로 메시지를 보내거나 서버에 업로드하지 않는다.

## 16. 직접 실행하는 순서

Python3.12 환경과 패키지는 `docs/agent_environment.md`를 참고한다. 프로젝트 루트에서 실행한다. 아래 명령은 원본을 덮어쓰지 않지만 고정 경로의 가공 산출물을 새로 만들 수 있으므로 기존 검증 결과를 보존하려면 결과별 폴더를 구분한다.

기초 특징을 새로 만들 때:

```powershell
./.venv-agent/Scripts/python.exe scripts/data_processing/run_preprocessing.py
./.venv-agent/Scripts/python.exe scripts/data_processing/analyze_card_complete.py
```

기존 인구 CSV·합산 배경 패킷을 준비한 뒤 성별 입력을 만든다:

```powershell
./.venv-agent/Scripts/python.exe scripts/data_processing/build_sex_features.py
```

기본 준비 출력은 data/processed/analysis_inputs이며 Agent도 이 폴더를 기본 입력으로 읽는다. --input-folder로 다른 준비 폴더를 지정할 수 있다. 성별 입력 파일·원본·기준 파일·코드가 바뀌면 manifest 검증이 막으므로 전처리를 다시 실행한다. 무조건 이전 해시를 고쳐 통과시키지 않는다.

API 없이 단계·순위·전달 프로필을 생성한다:

```powershell
./.venv-agent/Scripts/python.exe -X utf8 -B scripts/integration/run_analysis_agent.py --output data/processed/analysis_current --period 202512
./.venv-agent/Scripts/python.exe -X utf8 -B scripts/integration/verify_analysis_agent.py data/processed/analysis_current
```

키 설정 여부만 확인한다. 키 값은 표시하지 않는다:

```powershell
./.venv-agent/Scripts/python.exe scripts/integration/run_analysis_agent.py --check-config
```

외부 호출은 `.env`의 GEMINI_API_KEY·TAVILY_API_KEY와 `--mode gemini --web-search --research-mode focused --analysis-id ... --allow-external`이 필요하다. 승인된 전송 범위·호출 상한을 지키고 반복 실행하면 호출이 다시 발생한다는 점을 확인한다. 기본 offline 명령은 키가 있어도 API를 호출하지 않는다.

전달용 ZIP을 만들 때:

```powershell
./.venv-agent/Scripts/python.exe scripts/integration/build_welfare_handoff_package.py --results data/processed/analysis_current --output data/processed/hyeonji_handoff_current
```

## 17. 남은 연결과 한계

코드·출력·계약·실제 모델 연결 검증은 있고, 고립 정답 자료에 대한 정확도 검증은 없다. 웹 검색이 사회적 고립의 원인을 증명하지 않는다. 독립 계절성 추정·경제 지표 자동 편입·새 연도 원본의 자동 수집/전처리는 아직 아니다.

한수 쪽은 현재 출력 계약을 유지한다. 현지 쪽은 이 계약의 성별·연령 정의·partial/held를 수신부에 적용하고, 정욱 쪽은 실제 엔진 주입을 진행한다. 다른 팀의 기본 엔진에 stub이 남아 있는 상태와 분석 모듈의 계산 완료를 구분한다. 원본·출력은 Git에 없으므로 팀원의 로컬 데이터 준비도 확인해야 한다.

## 18. 왜 파일을 정리했는가

독립 수정 에이전트의 예전 실험 코드와 데모·초기 버스/검토 스크립트, 중복된 문서는 현재 분석 실행에서 사용하지 않아 브랜치에서 제외했다. 과거 기록은 `.local-archive/branch_cleanup_20261020/`에 보존했다. 현재 분석의 원본 재현에 필요한 보조 코드와 팀 공통 추천·기획·화면 코드는 남겼다. 실제 목록은 `docs/branch_cleanup_20261020.md`에 기록했다.
